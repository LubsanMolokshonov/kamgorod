# Блог → VK

CLI публикует только опубликованные статьи раздела blog с доступной страницей и её собственной обложкой.
Пост: заголовок, аннотация (или первые 300 символов текста), ссылка на сайт.
JPEG/PNG отправляются исходными байтами; WebP преобразуется в PNG без изменения размера и пикселей.
Генерации, подмены, кадрирования и резервных картинок нет.

## Подключение

1. Выполнить миграцию 192 штатной командой php migrate.php.
2. Получить через официальное приложение VK пользовательский access token администратора fgospro
   с правами photos и wall. Токен сообщества для сообщений не подходит для photos.getWallUploadServer.
   Использовать официальный OAuth-процесс доступного вам приложения; не вводить пароль в сторонние генераторы.
3. В закрытом .env задать VK_BLOG_USER_TOKEN, числовой VK_BLOG_GROUP_ID, VK_BLOG_ENABLED=false.
   Существующие VK_COMMUNITY_TOKEN и VK_GROUP_ID не менять. Секреты не передавать аргументами CLI.
4. Проверить php cron/publish-blog-vk.php --check-access. Проверяются fgospro, права пользователя,
   возможность загрузки фото и чтения стены; посты и фотографии не создаются.
5. Посмотреть php cron/publish-blog-vk.php: выводит подготовленные тексты и пути обложек всех
   доступных статей, без отправки, загрузки фото, миграций или записи очереди.
6. Зафиксировать архив: php cron/publish-blog-vk.php --initialize.
   Команда транзакционно записывает текущие опубликованные статьи как архив.
   Повторная инициализация запрещена, очередь не сбрасывается.
7. После проверки предпросмотра задать VK_BLOG_ENABLED=true и запустить --send.
   Первый запуск отправит одну старейшую архивную статью и все статьи после фиксации архива.
   Проверить запись в VK, её картинку и ссылку; повторный запуск в тот же день не отправит следующий архив.
8. Установить ежедневный cron после первой успешной проверки.

В .env значения задаются без кавычек (так устроен загрузчик проекта). Нужны PHP 8.2+, cURL, DOM, mbstring,
PDO MySQL и GD с WebP. Для первого подключения отдельный пользовательский токен обязателен.

## Расписание

Готовый systemd timer в scripts/systemd/fgos-vk-blog.timer задаёт часовой пояс явно.
Он не зависит от пояса хоста и запускает пропущенное задание после перезапуска.
После первой проверенной отправки установить на сервере:

    install -m 644 scripts/systemd/fgos-vk-blog.service /etc/systemd/system/
    install -m 644 scripts/systemd/fgos-vk-blog.timer /etc/systemd/system/
    systemctl daemon-reload
    systemctl enable --now fgos-vk-blog.timer
    systemctl list-timers fgos-vk-blog.timer
    journalctl -u fgos-vk-blog.service

Альтернатива — cron ниже. Использовать только один вариант.

Исполнять на сервере хоста, где доступен Docker pedagogy_web.
На cron с поддержкой CRON_TZ (Cronie):

    CRON_TZ=Europe/Moscow
    0 12 * * * docker exec pedagogy_web php /var/www/html/cron/publish-blog-vk.php --send >> /var/log/fgos-vk-blog.log 2>&1

На Debian cron CRON_TZ не гарантируется: проверить часовой пояс хоста (timedatectl).
Если хост UTC, поставить 0 9 * * *; если Europe/Moscow — 0 12 * * *.
Не менять часовой пояс сервера ради одной задачи. Ротацию лога добавить в logrotate.
Не устанавливать два расписания одновременно. Время квоты архива всегда Europe/Moscow.

## Гарантии и восстановление

Журнал vk_blog_deliveries хранит постоянную пару ID статьи/сообщества, ключ guid,
снимок поста и SHA256 исходной обложки, ID фото/поста, состояние и ошибки.
Правки статьи, даты, slug и повторная публикация не создают новую запись.
Записи VK никогда не редактируются, не удаляются и не восстанавливаются после ручного удаления.
Историю нельзя очищать при переустановке или восстановлении базы: это нарушает защиту от дублей.
При восстановлении старой резервной копии остановить интеграцию и сверить стену прежде включения.

Перед wall.post в базе фиксируется sending. При потере ответа/ошибке сохранения ID/остановке процесса
эта запись становится unknown (либо остаётся sending до следующего запуска).
Сверка читает до 1000 записей стены и подтверждает только единственный пост от сообщества
с точным текстом и сохранённым ID фотографии. Совпадение завершает операцию; отсутствие,
несколько совпадений или удалённый вручную пост НЕ разрешают повтор.
VK guid — дополнительная защита; код не полагается на неизвестный срок его хранения.
Автоматических повторов HTTP-запросов wall.post нет.

Для unknown проверить стену вручную и сохранённые payload/photo_id/attempted_at.
Если найдена запись, оператор может заполнить проверенный post_id и перевести её в sent.
Снимать unknown в pending допустимо только после подтверждения отсутствия поста и исключения
выполняющегося запроса; автоматической команды для этого намеренно нет.
Остальные статьи могут продолжать отправляться.
При явном отказе VK без создания поста операция остаётся pending.
При потере базы отправка немедленно прекращается. TelegramNotifier сообщает ошибки без токенов.

В день допускается одна выбранная пригодная архивная статья; после резервирования квоты ошибка не разрешает отправлять
следующую архивную в этот же день. Отсутствие страницы/обложки до резервирования квоты не блокирует остальные архивные статьи. Новые статьи идут первыми, без ограничения одной статьёй.
Просроченные новые статьи не теряются. Черновики и статьи с redirect_to_slug пропускаются.
Снятая с публикации статья проверяется повторно после загрузки фотографии.
Изменения сайта не блокируются сетевыми обращениями к VK; короткий промежуток между последней
проверкой и отправкой неизбежен без блокировки редакторского процесса.

Перед первым переносом сверить существующие ручные записи сообщества: ранее опубликованные
вручную статьи автоматически не распознаются как записи данной интеграции.

Отключение: VK_BLOG_ENABLED=false. Очередь и журнал сохраняются.
Обновлять истёкший токен только в .env, затем --check-access.

## Проверки

    php -d extension=pdo_sqlite tests/vk-blog-publisher-test.php

Тесты используют только SQLite в памяти и поддельные VK/сайт; обращений к сети и проектной базе нет.
Дополнительно php tests/vk-blog-mysql-test.php проверяет реальную миграцию и GET_LOCK двумя
сессиями локальной MySQL. Используются только TEMPORARY TABLE, постоянные таблицы не меняются.
Реальная авторизация и первая публикация проверяются при подключении токена VK.

## VK ID OAuth 2.1 + PKCE

Альтернатива ручному пользовательскому токену: короткий access token с ротацией refresh token.
Официальный VK ID SDK реализует `https://id.vk.ru/authorize` и POST `https://id.vk.ru/oauth2/auth`.
Источники: https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts и
https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/OAuth/User/DTO/Scopes.php.
Наличие wall/photos в SDK не гарантирует выдачу этих прав конкретному приложению:
проверить разрешения в кабинете VK ID и фактически выданный scope, затем --check.
Право offline в этом потоке не требуется. Старый код oauth.vk.com не подходит для VK ID PKCE.

1. В кабинете VK ID проверить приложение 54834138, разрешения wall/photos и зарегистрировать
   точный доверенный Redirect URI: https://fgos.pro/vk-blog-oauth-return.html.
   Публичная страница статическая, без SDK, обмена кода, JS и токенов.
2. В серверном .env задать VK_APP_ID=54834138 и
   VK_BLOG_REDIRECT_URI=https://fgos.pro/vk-blog-oauth-return.html.
   Оставить VK_BLOG_ENABLED=false и VK_BLOG_OAUTH_ENABLED=false до проверки.
3. На сервере выполнить `php scripts/connect-vk-blog.php --begin`.
   Команда создаёт случайные verifier/state на 15 минут, печатает URL с S256 challenge.
   Не строить ссылку вручную: verifier остаётся только на сервере.
4. Открыть URL, разрешить доступ. Сохранить code, device_id и state из адреса возврата в
   закрытом локальном файле; не отправлять в чат и не передавать аргументами команд.
   Передать JSON с этими тремя полями через stdin серверной команде
   `php scripts/connect-vk-blog.php --exchange`. Она обменивает код с серверного IP,
   проверяет scope/state, сохраняет токены и выполняет проверку прав без публикации.
5. Токены VK_ACCESS_TOKEN, VK_REFRESH_TOKEN, VK_DEVICE_ID, VK_TOKEN_EXPIRES_AT хранятся
   одной атомарно заменяемой JSON-записью. По умолчанию это .git/vk-blog-oauth/tokens.json,
   вне отслеживаемых файлов и закрытое Apache. Каталог 0700, файлы 0600, владелец — CLI-пользователь.
   Можно задать VK_BLOG_OAUTH_DIR на другом постоянном закрытом томе; не использовать /tmp
   или доступный по HTTP каталог. Не хранить ротируемую пару в .env: это предотвращает
   потерю ротации и затрагивание других настроек сайта. Каталог включить в закрытые резервные копии.
6. `php scripts/connect-vk-blog.php --check` должен пройти; после этого включить
   VK_BLOG_OAUTH_ENABLED=true. Старый VK_BLOG_USER_TOKEN при этом не используется.
   Первую отправку, фиксацию архива и включение расписания выполнить по основным шагам выше.

Перед API-запросами проверяется срок: за 600 секунд до истечения выполняется один refresh.
Обновление сериализовано файловой блокировкой; после захвата перечитывается свежая пара,
чтобы параллельный процесс не использовал старый refresh token. Оба новых токена сохраняются
до следующего запроса VK API. После явной ошибки API 5 допускается один refresh и один
повтор запроса. Ошибки прав 7/15 и другие отказы не запускают бесконечную переавторизацию.
Сетевой сбой wall.post не повторяется: остаётся прежняя сверка журнала и стены.

До refresh сохраняется состояние refreshing. Потеря ответа, остановка процесса или ошибка
записи после ротации блокирует дальнейшее использование пары: требуется ручная авторизация,
поскольку повтор старого одноразового refresh token может быть небезопасен. При отказе refresh
фиксируется reauthorization_required и безопасный last_error, без тела ответа и секретов.
Ежедневное задание уведомляет администратора существующим TelegramNotifier и сохраняет очередь.
Автоматический повтор самого refresh после неопределённого результата не выполняется.

Тесты: `php tests/vk-blog-oauth-test.php` и
`php -d extension=pdo_sqlite tests/vk-blog-publisher-test.php`.
Авторизация и токены относятся только к VK; генератор статей и его расписание не меняются.
