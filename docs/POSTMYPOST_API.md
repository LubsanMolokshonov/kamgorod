# Блог → Postmypost → VK

Единственный канал автоматической отправки — CLI `cron/publish-blog-postmypost.php`.
Внешняя публикация идёт через официальный REST API v4.1 Postmypost; генератор статей и его cron не меняются.
Исходный VK CLI выключен. RSS переводится в HTTP 410 при POSTMYPOST_BLOG_RSS_DISABLED=true,
чтобы модуль RSS не импортировал одновременно с API. Сам модуль в кабинете можно затем отключить.
Уже созданные внешние черновики не изменяются и не удаляются.

## Настройки

В закрытом серверном .env, без кавычек и без передачи секретов аргументами CLI:

```dotenv
POSTMYPOST_API_TOKEN=
POSTMYPOST_PROJECT_ID=368744
POSTMYPOST_ACCOUNT_ID=2363337
POSTMYPOST_BLOG_ENABLED=false
POSTMYPOST_BLOG_RSS_DISABLED=true
VK_BLOG_ENABLED=false
```

Группа фиксирована: 200065283. CLI проверяет account external_id=-200065283, chanel_id=2 и connection_status=1.
Публичный текст: заголовок, существующая аннотация (или первые 300 символов очищенного текста),
«Читать на сайте» и URL с `?utm_source=vk&utm_campaign=blog`. Никакой генерации изображений/текста.
VkBlogSite проверяет HTTP 200, canonical, точное соответствие pub-cover и cover_image_url, статус статьи до/после сети.
JPEG/PNG передаются исходными байтами через подписанную S3-форму; WebP переводится в PNG с сохранением пикселей.
Postmypost/VK могут технически перекодировать файл; кадрирование и изменение содержания интеграция не задаёт.
Отсутствующая/недоступная обложка откладывает статью с уведомлением.

## Журнал и расписание

Постоянная пара article/community остаётся в vk_blog_deliveries, архив — в vk_blog_channels.
Миграция 197 добавляет postmypost_blog_deliveries: provider_id, file_id, SHA256 исходного изображения,
полное подготовленное тело запроса и время принятия. Уникальны delivery_id и project/account/provider_id.
Инициализация при переходе сохраняет ранее зафиксированный архив и все sent/unknown; не сбрасывать журнал.
Новые статьи ищутся по source=blog/status=published без фильтра даты редактирования: пропуски после простоя догоняются.
Каждый дневной запуск: все новые статьи, затем одна старая в порядке published_at,id. Архивная квота — дата Москвы.
Сначала проверка страницы/обложки; квота архивной статьи резервируется перед созданием записи.
Временный отказ после резервирования не выпускает вторую архивную в этот день.

```sh
php cron/publish-blog-postmypost.php                    # только предпросмотр, без API/записи
php cron/publish-blog-postmypost.php --check-access     # GET, без постов/файлов
php cron/publish-blog-postmypost.php --initialize       # сохраняет существующий архив
php cron/publish-blog-postmypost.php --send --limit=1   # первая проверочная отправка
php cron/publish-blog-postmypost.php --reconcile        # только сверка; новых постов не создаёт
php cron/publish-blog-postmypost.php --send             # ежедневная отправка
```

Для send нужен POSTMYPOST_BLOG_ENABLED=true. --article-id ограничивает отправку одним ID.
GET_LOCK('fgos_vk_blog_200065283',0) общий с прежним VK CLI: параллельные отправители пропускают запуск.
Нельзя писать состояние/получить lock — не создавать пост. Публичный HTTP-доступ CLI запрещён.
Ключ операции — прежний постоянный SHA256(article/community). В API/официальном SDK не найден документированный
idempotency key для POST /publications, поэтому дополнительного гарантированного механизма на стороне сервиса нет.
Перед созданием сохраняются request_body и sending. Автоматических HTTP-ретраев на создание нет.
Потеря ответа/невалидный ответ/HTTP 5xx/ошибка сохранения → unknown; поиск по точному тексту, аккаунту и file_id
по всем страницам списка для явных post_date. Без post_date API возвращает только сегодняшний день:
проверяются даты ожидающих статей (UTC и Москва), даты сохранённых request_body, сегодня и завтра,
со всеми статусами 0,1,2,3,4,5,6,10,11,12. Это включает вчерашние RSS-черновики и отправки после простоя.
Одно совпадение принимается, отсутствие/несколько совпадений блокирует повтор.
Чтение неполного списка/ошибка API останавливает отправку. HTTP 400/401/403/404/422/429 до получения ID — явный отказ;
401/403/429 дополнительно останавливают текущий запуск. Неизвестные/временные ошибки до создания файла/поста
оставляют pending. Ошибка БД всегда прерывает канал, без очистки очереди.

После получения ID создаётся submitted; это не sent. В sent переводится только при наличии posts[] для целевого
аккаунта с post_status=1, external_id и URL именно wall-200065283_ID. Уже подтверждённые sent больше не проверяются
на наличие: ручное удаление не приводит к восстановлению. Submitted с ошибкой/черновиком/удалением → blocked,
автоматически новый объект не создаётся. Существующая внешняя публикация с URL статьи исключает новый POST:
опубликованная учитывается, черновик/неоднозначность → external_hold и уведомление администратора.
Единственный найденный черновик сохраняется по provider_id: монитор только читает его, не меняя и не публикуя.
Если администратор опубликует его вручную, монитор проверит URL статьи и запишет подтверждённый VK ID.
Внешние записи не редактируются и не удаляются. Факт принятия API с неполным ответом сохраняется до дополнительного GET.
После успешного create последующий 404 не разрешает новую отправку.

## Включение и контроль

1. Применить только согласованные миграции, проверить --check-access и --initialize.
2. Проверить предварительный просмотр, исходную обложку и ссылку выбранной статьи.
3. Отключить RSS на сайте, оставить прежний VK timer выключенным. Перенести токен защищённо.
4. При явном --send проверить одну статью, дождаться VK ID, повторить тот же ID: created=0.
5. Установить scripts/systemd/fgos-postmypost-blog{,-reconcile}.{service,timer}; daemon-reload.
6. Только после проверки включить POSTMYPOST_BLOG_ENABLED=true и два timer:
   - fgos-postmypost-blog.timer: старт ежедневно 12:00:00 Europe/Moscow, Persistent=true;
   - fgos-postmypost-blog-reconcile.timer: GET-сверка каждые 15 минут, без новых постов.

Фактическое появление в VK зависит от длительности загрузки и очереди Postmypost: 12:00 — старт задания,
а не гарантия публикации всех записей в одну секунду. Порядок передачи новые→архив гарантирует интеграция;
порядок окончательной обработки внешним сервисом может отличаться.
Контроль: journalctl -u fgos-postmypost-blog.service -u fgos-postmypost-blog-reconcile.service,
SQL state/last_error в vk_blog_deliveries. TelegramNotifier уведомляет при ошибках; токен и сырые ответы API не логируются.
При отключении: POSTMYPOST_BLOG_ENABLED=false и disable timer; очередь и журнал сохраняются.

Тесты: tests/postmypost-blog-test.php (SQLite), tests/postmypost-blog-mysql-test.php (только TEMPORARY TABLE и отдельный lock),
существующие tests/vk-blog-publisher-test.php и tests/blog-rss-test.php.
Источники протокола: https://github.com/postmypost/php-rest-sdk и https://help.postmypost.io/ru/docs/cookbook/file-upload.
