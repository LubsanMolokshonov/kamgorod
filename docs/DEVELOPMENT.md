# Разработка и проверка fgos.pro

Общий процесс — в [AGENTS.md](../AGENTS.md). Эта навигация основана на локальном коде,
конфигурации и доступных инструментах на 21.10.2026. Production в рамках настройки
стандарта не опрашивался. Старые отчёты описывают историю, а не доказанное текущее состояние.

## Окружения и запуск

- `Dockerfile`: PHP 8.2 Apache, Composer, pdo_mysql, GD, mbstring и другие расширения.
  Образ делает `composer install --no-dev`; CSS-minifier находится в `require-dev`.
  Для локальной сборки CSS нужны dev-зависимости в `vendor/` (обычный `composer install`,
  без изменения зависимостей). Bind mount репозитория перекрывает файлы образа, включая vendor.
- `docker-compose.yml`: web `8080`, phpMyAdmin `127.0.0.1:8081`, MySQL `127.0.0.1:3306`,
  AI `127.0.0.1:8083`; исходники смонтированы в `/var/www/html`, БД — в `db_data`.
  Имена контейнеров фиксированы, поэтому один `-p` не изолирует параллельные окружения.
- Требуется существующая внешняя сеть `docker-mailserver_mail_network`.
  На новой машине это предпосылка, не основание менять инфраструктуру автоматически.
- `.env` загружается самим PHP в константы; значения из файла могут перекрывать ожидания
  от environment Compose. Не считай префикс `DB_HOST=... php ...` гарантией смены БД.
  До подключения проверь механизм конфигурации, целевую БД и изоляцию без печати секретов.
- `.env.example` — перечень настроек, не готовая безопасная конфигурация. Не копируй рабочие
  credentials и пользовательские дампы для обычного теста. Отключи внешние интеграции
  в отдельной локальной конфигурации; один `EMAIL_SENDING_ENABLED` не выключает CRM, AI и мессенджеры.
- Обычный `docker compose up -d` запускает worker с `--send`; CMD web запускает cron,
  включая генерации и MAX-отправки. Даже локальный контейнер с рабочими ключами способен
  менять внешние системы. Не запускай его просто ради проверки документации.

Для отдельного подготовленного локального окружения без фоновой обработки:

```bash
docker compose config --quiet
# После проверки портов, сети, локальных настроек, отсутствия конфликта контейнеров:
docker compose up -d db
docker compose run --rm --service-ports --no-deps web apache2-foreground
```

Последняя команда запускает Apache в foreground, заменяя штатный CMD с cron; worker
не запускается. Она не отключает интеграции внутри HTTP-обработчиков. Схема из
`database/schema.sql` инициализируется только на пустом томе MySQL. Не удаляй том ради повторного запуска.
`php migrate.php` применяет ожидающие миграции и пишет `migrations`; это отдельное действие
с данными, не команда диагностики. Аналогично `php scripts/build-search-index.php` пишет индекс.
Остановку/удаление чужих QA-контейнеров и `docker compose down -v` не использовать для освобождения портов.

На этой машине при исследовании доступны PHP 8.2.33 с pdo_sqlite/GD/mbstring/pdo_mysql,
Node и Docker Compose v2. Штатный `pedagogy_web` не был запущен; существующие QA-контейнеры
не проверялись и не изменялись. Composer CLI в PATH не найден. Это снимок, перед задачей
проверяй инструменты заново. Production PHP/MySQL, secrets, cron и nginx требуют отдельной
проверки при порученном выпуске; локальный Docker не подтверждает их состояние.

## Проверки по риску

Единого PHP test runner/PHPUnit и корневого npm build в проекте нет. Используй существующие
CLI-файлы по теме; не запускай `tests/*.php` общим циклом без классификации побочных эффектов.

| Изменение / сценарий | Техническая проверка | Приёмка результата и побочные эффекты |
|---|---|---|
| Документы | ссылки на локальные файлы, согласованность команд, `git diff --check -- <свои файлы>` | Перечитать итоговый diff; выполнение описанных операций с данными не требуется |
| PHP/JS | `php -l <файл>`, `node --check <файл.js>` | Только синтаксис, без доказательства работы приложения |
| Глобальный CSS | `php scripts/build-assets.php`, diff бандла | Пишет tracked CSS; браузер desktop + mobile, картинки и пропорции, ошибки console/network |
| Конкурсы, курсы, поиск и SEO | `php tests/seo-technical-test.php`, выбранные Playwright specs | Каталог → фильтр/поиск → карточка → форма; запросы страниц могут писать визиты/аналитику |
| Олимпиады | `php tests/olympiad-page-content-test.php` (SQLite memory) | Реальная регистрация → тест → результат → PDF на тестовой учётке; создаёт данные |
| Запись на курс, CRM | `php tests/bitrix-payment-classification-test.php`, `php tests/course-access-task-test.php` (fake CRM, SQLite) | Тестовая заявка сохранена, сделка и задача видны в CRM, без дублей; реальные вызовы меняют CRM |
| Оплата / возвраты | `php tests/rnp-crm-course-revenue-test.php` (SQLite/fake CRM); отдельный DB-тест возвратов | Только в согласованной sandbox-среде: платёж → webhook → статус/суммы → доступ/PDF/уведомление; live-запросы могут двигать деньги и отправлять сообщения |
| Блог и очередь | `php tests/blog-queue-test.php`, `php tests/blog-schedule-test.php`, `php tests/blog-post-publisher-test.php` | В штатном режиме tmp + SQLite; нужны GD и pdo_sqlite. `BLOG_TEST_MYSQL=1` у publisher создаёт отдельную MySQL БД, это другой режим |
| Комментарии | `tests/blog-comments-test.php`, выбранный `blog-discussion.spec.js` | PHP-тест требует `BLOG_TEST_DB=pedagogy_blog_test_…`, создаёт таблицы/фикстуры. UI с mock API не доказывает сохранение и модерацию |
| Telegram / MAX | `php tests/ai-messenger-test.php`, `php tests/max-course-recommendation-test.php` | Парсер/политика/текст без доставки. Реальный клиент: сообщение → webhook/очередь → ответ → отписка; меняет БД, отправляет сообщения, AI может быть платным |
| Email-цепочки | lint и адресная проверка выбора получателей, статусов, locks/retry/caps по коду | Контролируемый адрес: статус провайдера + получение/ссылки/отписка. Dry-run не доказывает доставку; даже алерт может отправить письмо/Telegram |
| AI, материалы и публикации | lint, изолированная проверка правил, выбранный UI spec | Реальная генерация/адаптация может списать токены и вызвать платный API; PDF открыть и проверить содержимое/авторство/верстку |
| Миграция | ревью SQL, применение на одноразовой БД с нужной схемой | DDL/данные меняются; предварительно оценить locks, идемпотентность и восстановление; не применять к рабочей БД ради теста |

`tests/refund-accounting-test.php` подключает настроенный MySQL, создаёт временные таблицы.
`tests/olympiad-page-content-integration-test.php` пишет отзывы в транзакции и делает rollback.
`tests/seo-{catalog,material}-http-test.php` создают/удаляют фикстуры в настроенной БД и делают HTTP.
Новые `catalog-*-test.php` могут работать с БД, заказами и пакетами выпуска: сначала прочитай
конкретный тест. Очистка в finally/rollback не делает выполнение на рабочей БД нейтральным.
Фикстуры и тестовый HTTP-сервер должны использовать одну изолированную базу.

UI-команды — в [tests/ui/README.md](../tests/ui/README.md). Например, из корня:

```bash
npm --prefix tests/ui run test:smoke -- --project=desktop-chromium
# Выбранная тема на подготовленном локальном сервере:
cd tests/ui
BASE_URL=http://localhost:8080 npx playwright test course-detail.spec.js --project=desktop-chromium
```

Playwright запускает desktop Chromium и mobile WebKit, но не поднимает сервер.
Даже smoke загружает трекеры и может создавать записи о визитах, вызывать стороннюю аналитику.
`npm run test:prod` — существующая команда с внешними побочными эффектами, не базовая проверка.
HTTP 200, сборка, fake CRM и имитация SDK не доказывают сохранение заявки, оплату или доставку.
После автоматизации укажи, какие реальные шаги пользователя остались непроверенными.
Новые тесты добавляй для значимого изменения поведения/регрессии, а не для каждой правки текста.

## Выпуск и восстановление

Только по поручению пользователя: [навык деплоя](../.agents/skills/fgos-deploy/SKILL.md),
его источник — [процедура выпуска](../.claude/commands/deploy.md). Не применять старый
`docs/DEPLOYMENT.md`. Разрешённые уже в задаче действия повторно согласовывать не нужно.

Процедура указывает `root@141.105.69.45`, `/var/www/kamgorod`, Git `origin/main`,
`pedagogy_web`/`pedagogy_db`: целевой diff → CSS при необходимости → согласованный коммит/push →
проверка серверного Git → именованный stash серверных правок → pull → восстановление stash →
нужные миграции → restart → HTTP/логи + сценарий затронутого продукта. При конфликте остановиться.
До выпуска проверь фактическую ветку/remote, исходный SHA, состояние сервера и резервную копию
данных для изменений схемы/контента. Не включай все грязные файлы в выпуск автоматически.

В существующем runbook нет универсальной команды rollback и проверенного восстановления БД.
До рискованного выпуска определи совместимость старого кода с новой схемой и доступный backup.
При сбое сохрани логи и SHA, останови последующие шаги; восстанови согласованную предыдущую
версию через Git с сохранением серверных правок, затем повтори smoke и продуктовую приёмку.
Не используй безусловный reset или обратную миграцию. Откат кода не откатывает БД, платежи,
письма и CRM. Для них нужен отдельный предметный способ исправления/восстановления.
Путь, свежесть backup и команда restore должны быть проверены в конкретной задаче; сейчас они неизвестны.
Nginx хранится вне Git — [docs/NGINX_PROD.md](NGINX_PROD.md) описывает историческую настройку.
