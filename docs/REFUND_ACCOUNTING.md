# Учёт возвратов в РНП

Подтверждённая API ЮKassa сумма `refunded_amount` хранится отдельно в
`yookassa_refund_totals` по ID платежа. Исходная стоимость заказа не меняется.
Повтор webhook или сверки не дублирует сумму; старый ответ API не уменьшает
уже учтённый возврат. Pending/canceled возвраты не принимаются.

РНП вычитает возврат из периода исходной продажи, сохраняя выбранную атрибуцию
paid/created. Портал использует сумму заказа, токены — сумму покупки,
курсы — OPPORTUNITY выигранной сделки Bitrix24. При смешанном заказе возврат
распределяется пропорционально ценам позиций. Полностью возвращённая продажа
не считается оплатой; число созданных заказов сохраняется. Средний чек, прибыль,
ROMI и графики используют скорректированную выручку.

OPPORTUNITY в CRM предполагается исходной суммой до возврата. Если менеджер
самостоятельно уменьшает её на тот же возврат, получится двойной вычет.
Сделки без связи через course_enrollments/order_items нельзя автоматически
сопоставить с платежом. Старый статус refunded без записи сверки трактуется как
полный возврат; сверка уточняет фактическую сумму.

Webhook проверяет возврат и исходный платёж через API магазина. Частичный
возврат не запускает прежний обработчик полного возврата с отзывом доступа.
Историческая/периодическая сверка исправляет только финансовый учёт, не отзывает
документы, токены и доступ. Успешная оплата и история заказа остаются сохранены.
Другие аналитические разделы вне РНП используют свои расчёты и здесь не меняются.

## Внедрение после отдельного запроса на деплой

1. Сохранить резервную копию БД согласно runbook деплоя.
2. Применить миграцию `190_yookassa_refund_totals.sql` перед открытием обновлённого РНП.
3. Выполнить `docker exec pedagogy_web php scripts/reconcile-refunds.php`:
   по умолчанию это dry-run всей доступной истории ЮKassa, без записи.
4. Выполнить `docker exec pedagogy_web php scripts/reconcile-refunds.php --apply`.
   Проверить `errors=0`, отдельно разобрать `unlinked`; повтор запуска безопасен.
5. Проверить РНП по периодам исходных продаж в режимах paid/created, затем повторить
   сверку и убедиться, что суммы не изменились повторно.
6. Проверить подписку `refund.succeeded` в личном кабинете ЮKassa и активность
   существующего cron `reconcile-payments.php`. Cron дополнительно проверяет
   возвраты за последние 30 дней; после простоя более 30 дней повторить полную сверку.

Локальные проверки:

```sh
docker exec pedagogy_web php tests/refund-accounting-test.php
docker exec pedagogy_web php tests/rnp-crm-course-revenue-test.php
```

Первый тест использует временные таблицы MySQL текущего соединения и подмену API,
второй — SQLite и подмену Bitrix24. Реальные платежи/возвраты тесты не создают.
