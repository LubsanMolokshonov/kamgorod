# Публикация согласованного комплекта

## Автоматическая постановка в очередь

Постоянное поручение пользователя от 16.10.2026: после создания готовой статьи
автоматически добавлять её в конец очереди, по одной статье в день. Время —
09:00 Europe/Moscow, то есть 13:00 Asia/Ho_Chi_Minh. Это разрешение относится к
новым редакционным материалам и их постановке в очередь, не к перезаписи уже
опубликованных текстов. Просьба «только черновик» имеет приоритет.

`editorial-init-article.php` создаёт незавершённый комплект и дату не резервирует.
Автоматический финальный шаг навыка выполняется после текста, источников,
обложки, содержательной и технической проверки:

```bash
php scripts/editorial-check.php --article=<slug>
php scripts/add-blog-post.php --manifest=editorial/articles/<slug>/metadata.json --validate-only
php scripts/enqueue-blog-post.php --manifest=editorial/articles/<slug>/metadata.json --enqueue --approved-sha256=<полученный-хеш>
```

Последняя команда сама запускает editorial-check. Она учитывает даты всех активных
JSON в `editorial/schedules/`, выбирает день после хвоста и сохраняет статью в
`daily-queue.json`. Если хвост в прошлом или очередь пуста, берётся ближайшее
будущее 09:00 МСК. Без `--enqueue` выводится предварительная дата, очередь не
меняется. Без актуального SHA256 запись запрещена. Повтор с той же версией
возвращает прежнюю дату, изменённый запланированный комплект не подменяет.
Сохраняются также SHA256 inline-иллюстраций. Даты и JSON записываются атомарно
под общей блокировкой; будущие статьи в БД заранее не создаются.

После добавления разверни только относящиеся к задаче комплекты, ассеты,
скрипты и расписание через `fgos-deploy`. Действующее поручение на автоматическую
очередь разрешает этот ограниченный деплой. Не добавляй чужие рабочие изменения.
На сервере выполни dry-run `process-blog-schedule.php` для затронутых расписаний.
Убедись, что установлен host `/etc/cron.d/fgos-blog-daily-queue` из
`editorial/schedules/daily-queue.cron`: он проверяет срок каждые пять минут и
не ограничен октябрём или конкретным годом. При уже установленном cron не
создавай дубль. Сохрани дату и серверный результат в review.md.

В расписаниях есть опубликованные записи. При правке следующих статей
не меняй файлы уже вышедших комплектов в этом релизе: строгий повтор сравнивает
их с БД и остановится на конфликте. Непубликуемую новую редакцию сохраняй
отдельно до самостоятельного запроса на её выпуск.

## Предварительные проверки

Локально (если PHP доступен только в Docker, используй образ проекта):

```bash
php scripts/editorial-check.php --article=<slug>
php scripts/add-blog-post.php --manifest=editorial/articles/<slug>/metadata.json --validate-only
php scripts/add-blog-post.php --manifest=editorial/articles/<slug>/metadata.json
```

Первая команда проверяет компактный комплект, ссылки и карточки библиотеки источников.
Вторая проверяет только файлы и выводит SHA256. Третья проверяет БД и занятость
slug без записи. Dry-run не резервирует slug; при записи проверка повторяется под
MySQL GET_LOCK. CLI требует обложку и явный slug. Старые вызовы без --publish больше
не создают статью. `--approved-sha256` защищает версию, но не заменяет согласие человека.

После согласования: проверить локальный diff и серверный git status; закоммитить
только изменения задачи, запушить и подтянуть конкретный проверенный коммит. Не
перезаписывать чужие серверные файлы и не переносить .env. При расхождении истории
разобраться до pull. Нужные артефакты должны входить в коммит. Эта задача не требует
миграций; не запускать все миграции попутно. Проверить Apache configtest и PHP syntax.

Сначала серверный dry-run, затем:

```bash
docker exec -w /var/www/html pedagogy_web php scripts/editorial-check.php --article=<slug>
docker exec -w /var/www/html pedagogy_web php scripts/add-blog-post.php --manifest=editorial/articles/<slug>/metadata.json --publish --approved-sha256=<согласованный-хеш>
```

Сравнить хеш с одобренным локальным комплектом. Все вставки и cover_status=done
в одной транзакции: cron не должен подменять готовую обложку. При ошибке до commit
записи откатываются. После сетевого обрыва сначала проверить существующий slug;
не считать повторный запуск разрешением на перезапись.

## Приёмка

Проверить HTTP 200 статьи и изображения, точный текст, H1, Title/Description,
canonical, robots, Open Graph и Article JSON-LD, каталог `/blog/` и sitemap.
Проверить на мобильном ширину таблиц, читаемость и изображение; не публиковать
служебные пути (доступ к editorial и .agents должен возвращать 403).
Если запись прошла, а страница неисправна, сначала зафиксировать ID. Убрать из
публикации только эту новую запись до исправления; не удалять другие статьи.
Любой содержательный пересмотр снова согласовать. В review.md записать URL, ID,
коммит, время и результаты реально выполненных проверок, включая ограничения.
